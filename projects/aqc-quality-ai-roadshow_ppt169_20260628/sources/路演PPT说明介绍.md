## 一、整体叙事主线

### 路演一句话

这是一套面向钢铁质量管理的规则优先型 AI 增强系统：结构化标准负责判定，传统流程负责闭环，AI 负责标准检索、判定解释、风险提示、问答与审计追踪，做到可引用、可降级、可复核、可推广。

### 推荐叙事顺序

1. 先讲痛点：标准多、规则复杂、人工查证慢、异常流程责任重、AI 容易“说得像但无依据”。

## 第 3 页：业务痛点总览

### 页面目标

说明为什么质量管理场景需要 AI，但不能简单交给 AI。

### 建议画面

五个痛点卡片或流程断点图。

### 页面文案

钢铁质量管理的典型痛点：

- 标准多：国标、企标、客户协议并存，版本、生效期、适用范围复杂。
- 判定严：合格、不合格、需复检、可让步、标准冲突对应不同业务责任。
- 查证慢：人工翻 PDF、表格、协议，定位条款和限值成本高。
- 解释难：自动判定给出结论后，销售、生产、客户往往还要追问依据。
- 风险重：让步接收、改判、冲突裁决和质保书出证都需要可追溯证据。

### 讲解稿

质量判定不是一般问答。一个指标的上下限可能来自客户协议，也可能来自企业标准或国标；同一指标还可能存在让步范围、复检规则和标准冲突。AI 如果直接给结论，一旦引用错标准或编造限值，风险非常高。因此我们的设计不是让 AI 做判定，而是让 AI 在有证据的地方帮助人理解、核查和决策。

## 第 4 页：系统角色定位：规则、人、AI 三方分工

### 页面目标

明确 AI 的边界，回应“AI 能力与角色职责是否匹配”。

### 建议画面

三栏图：规则引擎、人、AI。

### 页面文案

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 规则引擎 | 基于结构化标准产生质量判定 | 不生成业务解释长文 |
| 人工流程 | 发起复检、审批改判、确认让步、裁决冲突 | 不再手工翻查全部依据 |
| AI | 检索标准、解释判定、给建议、评估风险、问答 | 不自动放行、不自动审批、不覆盖结构化限值 |

### 讲解稿

系统的核心红线是结构化标准数据是判定唯一真相源。RAG 查到的原文用于解释和引用，不能覆盖结构化限值。AI 输出必须能降级，必须可审计，缺少证据时必须明确说缺证据。

### 页面文案

- 维护国标、企标、客户协议、版本、生效期、客户、品种、牌号、规格范围。

- 发布后对源文件逐个解析、分块、向量化和索引。
- 草稿标准可保存文件，但不进入正式 RAG 检索。

### 讲解稿

- 代码资源：`SourceDocumentTextExtractor` 多实现、`StandardClauseChunker`、`qc_standard_document`、`qc_standard_clause`

### 页面文案

判定引擎读取：

- 检验记录：炉号、卷号、批次、客户、品种、牌号、规格、样品类型。
- 检验值：成分、力学性能、尺寸等指标。
- 标准限值：合格上下限、让步上下限、适用范围。

单指标判断顺序：

1. 在合格范围内 -> 合格
2. 超合格限但在让步范围内 -> 可让步
3. 超合格限且未配置让步范围 -> 需复检
4. 超出让步范围 -> 不合格

### 讲解稿

规则判定会生成判定结果和判定依据快照。快照保留当时匹配到的标准、指标限值、实测值、偏差和触发规则，这样后续标准变更不会影响历史判定的可追溯性。

## 第 9 页：异常处置闭环

### 页面目标

展示系统不是只给结论，而是有完整后续流程。

### 建议画面

以判定结果为入口的分流图。

### 页面文案

```text
NEED_REINSPECTION -> 复检管理 -> 新检验记录 -> 重新判定
UNQUALIFIED/其他 -> 改判申请 -> 审批通过 -> 新最终结论
CAN_CONCESSION -> 让步接收 -> 客户确认/双签审批 -> 允许放行
STANDARD_CONFLICT -> 人工裁决控制标准 -> 规则重判 -> 新最终结论
```

### 讲解稿

复检是重新测，改判是人工修正结论，让步是风险可控情况下的接收审批，标准冲突是人工裁决后再由规则引擎重判。它们是并列的业务通道，AI 只能辅助说明和预填，不直接创建或审批记录。

### 页面文案

标准 RAG 流程：

```text
源文件上传
  -> 文本提取
  -> 确定性条款分块
  -> MySQL 条款落库
  -> Embedding 向量化
  -> ES 向量索引
  -> 用户自然语言提问
  -> Query Embedding
  -> 向量/关键词检索
  -> Grounded Chat
  -> 引用校验
  -> 回答或降级展示
```

### 讲解稿

RAG 不是把整份标准塞给模型，而是先做可复现的条款分块和索引。用户提问后，系统只把检索到的条款交给模型，并要求回答附来源编号。模型输出再经过引用校验，不能从记忆里编标准。

### 效果对比

| 方式 | 结果 |
| --- | --- |
| 人工翻标准 | 慢，容易漏版本和适用范围 |
| 传统关键词 | 只返回文档片段，需要人工判断 |
| 本系统 RAG | 返回答案、来源条款、版本、页码、分数和检索模式 |

### 页面目标

### 建议画面

三种状态卡片：正常回答、低相关仅展示、注入防护。

### 页面文案

RAG 安全策略：

- 无证据：拒绝从模型记忆回答。
- 低相关：只展示参考条款，不生成权威回答。
- Prompt 注入：检测“忽略标准、编造、绕过、泄露提示词”等指令，跳过 Chat，仅展示检索条款。

### 讲解稿

RAG 的价值不只在“能回答”，更在“不能回答时会拒绝”。这避免了模型把没有来源的说法包装成标准结论。当前测试报告也诚实记录了一个边界：当向量索引增多后，极低相关或注入用例可能命中参考段落，后续需要继续校准阈值和拒答策略。

## 第 27 页：RAG 架构原理

### 页面目标

用一页讲清楚标准 RAG 的两条流水线。

### 建议画面

左右两条流水线：入库链和查询链。

### 页面文案

入库链：

```text
源文件 -> 文本提取 -> 条款分块 -> MySQL 条款 -> Embedding -> ES 索引
```

查询链：

```text
问题 -> Query Embedding -> ES Hybrid 检索 -> 来源治理 -> Grounded Chat -> 校验与降级
```

设计原则：

- 分块确定性，不让 Embedding 模型决定 chunk 边界。
- 源文档文本只做引用证据，不修改结构化限值。
- 检索结果带标准编号、版本、条款号、页码、文件名、分数。
- ES 不可用时可退回 MySQL 关键词兜底。

### 讲解稿

RAG 的关键不是只接一个向量库，而是将“可追溯来源”和“可替换技术”分开。MySQL 保存条款和元数据，ES 保存向量索引，模型只对检索到的条款进行 grounded 回答。

## 第 32 页：AI 置信度机制

### 页面目标

讲清楚 confidenceLabel 的含义和业务作用。

### 建议画面

HIGH / MEDIUM / LOW 三档卡片和触发条件。

### 页面文案

AI 置信度评价的是“这次 AI 输出能不能放心用”，不评价产品是否合格。

主要字段：

- `confidenceLabel`：HIGH / MEDIUM / LOW
- `confidenceScore`：0-1 分数
- `confidenceFactors`：影响因素

当前主要规则：

- `STANDARD_CONFLICT`、未裁决阻断冲突、标准覆盖缺口 -> LOW
- 引用命中 + AI 解释通过校验 -> HIGH
- 引用命中但模型解释不可用 -> MEDIUM
- 规则完整但引用缺失 -> MEDIUM，并标记 citationMissing

业务作用：

- 低置信复检/改判建议 withheld
- 让步低置信要求人工评审
- 工作台统计低置信复核
- AI 评估审计按置信度筛选

### 讲解稿

置信度不是模型自评“我觉得很准”，而是由结构化规则、RAG 引用、冲突状态和输出校验共同决定。OpenSpec 设计了 rule/RAG/LLM 权重配置，默认 0.6/0.3/0.1；当前系统已有配置入口，但主链路仍主要使用确定性门禁规则，这是后续扩展的一个清晰方向。

## 第 33 页：模型输出校验：不让 AI 编造标准

### 页面目标

解释 HIGH 置信度和“引用通过校验”到底做了什么。

### 建议画面

四道门禁流程图。

### 页面文案

`acceptTrustedCitedOutput()` 四道门禁：

1. 输出非空，引用列表非空。
2. 每条引用都有段落正文。
3. 输出必须出现 `[1]`、`[2]` 或条款号。
4. 每个引用编号所在句子提到的指标、数值、限值，必须能在对应来源段落或结构化依据中找到支撑。

拒绝规则：

- 不能用“适用范围”章节引用具体限值。
- 不能用“术语定义”章节引用合格上下限。
- 不能引用不存在的编号。
- 不能写来源条款中没有的数值或结论。

### 讲解稿

这不是让模型自己解释为什么可信，而是后端逐条检查。比如模型写“Rm 合格范围为 370-510 MPa[1]”，那 `[1]` 对应段落里必须真的有这个范围。如果 `[1]` 是“本文件适用于冷轧板”的范围章节，整段输出会被拒绝并降级。

### 1. 合格样例

用于展示：

- 检验录入
- 自动判定 `QUALIFIED`
- 判定解释引用完整
- 质保书数据生成
- 质保书问答“为什么能出证”

### 2. 不合格样例

用于展示：

- 指标低于或高于结构化限值
- 判定解释说明偏差
- AI 复检建议
- 质保书正式生成被拒

### 3. 可让步样例

用于展示：

- 指标落入让步带
- AI 让步风险评估
- 风险等级、建议条件、替代库存、历史案例
- 人工审批仍是最终动作

### 4. 标准冲突样例

用于展示：

- `STANDARD_CONFLICT`
- 判定解释 LOW
- 复检/改判建议 withheld
- 让步风险 `BLOCKED`
- 质保书禁止正式生成
- 人工裁决后规则重判

### 5. Prompt 注入或无证据样例

用于展示：

- 标准 RAG 不从模型记忆回答
- 低相关只展示参考条款
- 检测注入指令后跳过 Chat

## 六、路演口径红线

不要说：

- “AI 自动判定产品合格。”
- “AI 可以自动批准让步。”
- “RAG 检索到的标准原文会覆盖结构化标准限值。”
- “标准冲突时 AI 会直接裁决。”
- “置信度由模型自己判断。”
- “Prompt 可以在页面上任意实时修改并绕过校验。”

建议说：

- “AI 只解释、检索、建议和评估，最终判定和审批由规则和人控制。”
- “结构化标准是唯一判定真相源，RAG 原文只做引用和解释。”
- “低置信、缺证据和标准冲突会触发降级、阻断或人工复核。”
- “Prompt 版本已经资源化并进入审计，后续可以扩展前端对比和灰度能力。”
- “系统保存 AI 输入、输出、引用、版本、置信度和采纳状态，方便回放和追责。”

## 七、PPT 视觉风格规范：对齐当前系统 UI

### 设计语言

PPT 整体应延续系统前端的视觉语言：

```text
AQC 工业精密控制室
Industrial Precision Control Room
```

关键词：

- 深色工业后台
- 精密控制室
- 高对比数据面板
- 青色科技强调
- 细边框、低圆角、紧凑信息密度
- 真实业务界面优先，不做营销风落地页

### 色彩规范

PPT 建议直接沿用系统 CSS Token，避免另起一套视觉体系。

| 用途 | 颜色 | Hex |
| --- | --- | --- |
| 页面主背景 | 深蓝黑 | `#060E1C` |
| 面板背景 | 工业深蓝 | `#0B1929` |
| 卡片背景 | 深蓝卡片 | `#0F2137` |
| 悬停/强调底 | 蓝灰 | `#162C47` |
| 普通边框 | 深蓝边框 | `#1A3352` |
| 亮边框 | 蓝灰亮边框 | `#234569` |
| 主文字 | 近白蓝 | `#E8F0FA` |
| 标题文字 | 高亮白蓝 | `#F4F8FC` |
| 次级文字 | 浅蓝灰 | `#C4D8EC` |
| 弱文字 | 灰蓝 | `#9BB8D4` |
| 主强调 | 青色 | `#00D4FF` |
| 成功/合格 | 绿色 | `#16C974` |
| 危险/不合格 | 红色 | `#FF3B5C` |
| 警告/待复核 | 橙色 | `#FF8C00` |
| 信息/复检 | 蓝色 | `#3D9EFF` |
| 重点提示 | 金色 | `#FFB400` |

使用建议：

- 背景统一使用 `#060E1C`，不要使用白底、浅灰底或大面积渐变。
- 卡片和表格使用 `#0B1929` / `#0F2137`，用 `#1A3352` 做 1px 边框。
- 青色 `#00D4FF` 只用于关键路径、主按钮、当前页标题线、AI 节点和高亮数字。
- 红、橙、绿只用于语义状态，不做装饰色。
- 单页强调色不超过 2 种，避免变成彩色信息噪声。

### 字体规范

系统字体栈：

- UI 字体：`IBM Plex Sans` / `Helvetica Neue` / sans-serif
- 数据字体：`IBM Plex Mono` / `Courier New` / monospace
- 压缩标题：`IBM Plex Sans Condensed` / `Arial Narrow`

PPT 可执行替代：

- 若制作环境有 IBM Plex，优先使用 `IBM Plex Sans` 和 `IBM Plex Mono`。
- 若没有，中文使用 `Microsoft YaHei` 或 `PingFang SC`，英文和数字使用 `Consolas` / `DIN` / `IBM Plex Mono`。
- 数据、编号、接口名、表字段、置信度分数使用等宽或类 DIN 字体。

字号建议：

| 元素 | 建议字号 |
| --- | ---: |
| 封面标题 | 40-48 |
| 章节页标题 | 34-40 |
| 普通页标题 | 26-30 |
| 卡片标题 | 16-18 |
| 正文要点 | 14-16 |
| 表格正文 | 11-13 |
| 数据大数字 | 32-44 |
| 页脚来源/备注 | 9-10 |

排版注意：

- 不使用负字距。
- 不使用花体、手写体、圆润可爱字体。
- 不把正文做成大段居中，业务说明保持左对齐。
- 中文和英文混排时，英文接口名、枚举值、表名保持等宽风格。

### 页面结构

推荐统一版式：

```text
顶部：页标题 + 细青色状态线 / 页码
中部：主内容区，2-3 栏网格
底部：来源、演示记录、关键结论或下一步
```

版面规则：

- 每页使用 12 栏或 3 栏网格，内容边距保持一致。
- 卡片圆角控制在 4-8px，贴近系统 `el-card` 的克制感。
- 尽量使用全宽信息带、表格、流程图和数据卡，不做大面积悬浮卡片堆叠。
- 一页只讲一个主结论；复杂流程拆成“总览页 + 细节页”。
- PPT 不做营销 hero 风格，不使用大幅渐变背景、装饰光斑、漂浮圆球。

### 卡片与面板样式

卡片建议：

- 背景：`#0B1929` 或 `#0F2137`
- 边框：1px `#1A3352`
- 圆角：4-8px
- 阴影：弱化或不用阴影，最多使用 `rgba(0,0,0,0.35)` 的轻阴影
- 标题区：可使用更深的 `#0F2137` 顶栏

状态卡片：

- `QUALIFIED` / 通过：绿色数字或左边框
- `UNQUALIFIED` / 拦截：红色数字或左边框
- `NEED_REINSPECTION` / 复检：蓝色
- `CAN_CONCESSION` / 让步：橙色
- `STANDARD_CONFLICT` / 冲突：红色 + 橙色双提示
- `HIGH`：绿色或青色
- `MEDIUM`：橙色
- `LOW`：红色

卡片内容不要写成长段说明，应采用：

```text
短标题
关键数字 / 状态
一行解释
来源或跳转提示
```

### 表格规范

PPT 表格应模拟系统 `el-table` 的风格：

- 表头背景：`#0F2137`
- 表体背景：`#0B1929`
- 表格边框：`#1A3352`
- 表头文字：浅蓝灰、等宽、字号略小
- 关键状态用标签色，不用整行大面积红绿背景

适合做成表格的内容：

- 评分维度映射
- 业务场景对比
- AI 能力与业务节点
- Prompt 场景对比
- 降级路径
- 成本项
- 已知限制和应对策略

### 图表规范

图表应像质量工作台的统计面板，而不是商业汇报图。

建议：

- 折线/柱状图使用深色背景和细网格线。
- 主要系列用青色，异常系列用红/橙，合格系列用绿。
- 坐标轴文字使用灰蓝，网格线使用 `#1A3352`。
- 数字指标用大号等宽字体。
- 图例放右上或底部，避免占用主视觉。

不建议：

- 使用 3D 饼图。
- 使用彩虹色图表。
- 使用浅色 Excel 默认图表。
- 使用过多阴影和立体效果。

### 流程图规范

流程图是本 PPT 的重点，建议统一样式：

- 节点：深色矩形，4-6px 圆角，1px 蓝灰边框。
- 主流程箭头：青色。
- 人工节点：橙色边框或橙色角标。
- 阻断节点：红色边框。
- 规则引擎节点：蓝色。
- AI 节点：青色。
- 数据库/审计节点：绿色或蓝灰。

推荐节点标识：

```text
[规则] JudgmentEngine
[AI] ModelGateway.chat
[RAG] VectorStoreGateway.searchClauses
[人工] 冲突裁决 / 审批
[审计] qc_ai_assessment
[阻断] STANDARD_CONFLICT / LOW
```

### 截图使用规范

系统截图是最有说服力的素材，应保持真实业务后台感。

截图建议：

- 使用深色系统原始截图，不要改成浅色。
- 截图外框使用 1px `#234569`，圆角 4px。
- 局部放大时，用青色描边框标注关键区域。
- 关键字段可用小标签标出，如 `confidenceLabel`、`degradationSource`、`promptVersion`。
- 页面截图不要模糊、过暗或过度裁切，评委要能看清真实系统内容。

截图页布局：

```text
左侧：真实系统截图，约 60%-70% 宽度
右侧：3-5 条解释标签
底部：一句业务结论
```

### 截图占位标记规范

本文档中所有需要后期插入真实系统运行截图的位置，统一使用如下格式：

```text
[截图占位 Sxx：截图名称]
建议截图内容：说明需要截取的页面、字段和状态。
建议比例：说明适合全屏、宽图、局部弹窗还是缩略图矩阵。
后期处理：说明插入截图后的标注方式。
```

后期制作 PPT 时：

- 保留 `Sxx` 编号，方便从本文档追溯到 PPT 页面。
- 将占位块替换为真实系统运行截图，不使用示意图冒充真实界面。
- 如果一页需要多张截图，按 `SxxA`、`SxxB`、`SxxC` 排列。
- 截图尽量使用同一浏览器宽度和同一账号，保持菜单、顶栏、字体和颜色一致。
- 如截图包含敏感客户或账号信息，先用同色深色遮罩做局部脱敏，保留字段结构。
- 替换完成后可删除占位文字，但建议在 PPT 备注里保留截图编号。

### 图标与标记

PPT 图标风格应贴近 Element Plus / Lucide 的线性图标：

- 使用线性图标，不使用卡通插画。
- 图标线宽保持一致。
- 图标颜色使用当前语义色。
- 图标只辅助识别，不替代文字说明。

建议对应：

- 标准/RAG：文档、搜索
- 判定：印章、校验
- 复检：刷新
- 改判：编辑
- 让步：检查、警告
- 冲突：告警、关闭
- 审计：锁、列表
- 模型网关：节点、连接

### 动效规范

如果制作动态 PPT，保持克制：

- 流程图可按步骤淡入。
- 演示链路可用青色线条逐段出现。
- 不使用弹跳、旋转、飞入等夸张动画。
- 过渡统一使用淡入或轻微平移。

### PPT 母版建议

建议制作 5 类母版：

1. 封面页：深色背景 + AQC 标识 + 大标题。
2. 章节页：左侧章节编号，右侧一句核心判断。
3. 流程页：顶部标题，中部大流程图，底部红线说明。
4. 截图页：大截图 + 右侧解释标签。
5. 数据页：指标卡 + 表格 / 图表。

母版固定元素：

- 左上角：`AQC / ai-quality-control`
- 右上角：章节名或页码
- 底部细线：`#1A3352`
- 当前重点页可加一条青色 2px 线

### 禁用风格

不要使用：

- 白底商务模板
- 大面积紫色、蓝紫渐变、霓虹光斑
- 互联网 SaaS 营销风 hero 页
- 卡通人物、AI 机器人插画
- 玻璃拟态毛玻璃大卡片
- 圆角过大的胶囊按钮
- 大段居中文字
- 3D 图标和立体阴影
- 与系统不一致的红绿灯式大色块背景

### 可直接放入 PPT 制作要求的一句话

PPT 视觉必须与当前 AQC 系统保持一致：采用深色工业精密控制室风格，以 `#060E1C` 为主背景，`#00D4FF` 为主强调色，辅以绿色/橙色/红色表达质量状态；页面结构以紧凑卡片、表格、流程图和真实系统截图为主，避免营销化、插画化、浅色商务模板和过度装饰。

## 八、制作 PPT 时的视觉建议

- 首页和业务闭环页使用真实系统截图，不使用营销式插画。
- 业务流程页优先用清晰流程图，不堆文字。
- AI 场景页用“输入、处理、输出、门禁”四段式布局。
- 技术页用分层架构图：业务层、AI 网关层、外部模型/向量库层。
- 可观测性页用审计详情截图或字段表。
- 成本和限制页用表格，显得工程化、可信。
- 每个场景至少保留一个“AI 不做什么”的边界提示。
