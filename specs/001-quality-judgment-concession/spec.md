# Feature Specification: 质量判定解释与让步管理系统

**Feature Branch**: `001-quality-judgment-concession`

**Created**: 2026-05-14

**Status**: Draft

**Input**: 赛题四：质量管理｜质量判定解释与让步管理系统

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 标准库维护与自动判定（Priority: P1）

质量工程师需要维护国标、企标和客户协议标准，并在检验录入后，系统自动按客户和产品匹配适用
标准输出判定结论（合格 / 不合格 / 需复检 / 可让步），且每条结论必须能展示其判定依据。

**Why this priority**: 这是整个系统的核心能力——没有标准维护和自动判定，所有下游流程（复检、
改判、让步）均无法启动。判定依据透明是解决"销售和生产难复核"问题的根本。

**Independent Test**: 维护一条客户协议标准后，录入一组检验值，系统能输出带依据的判定结论，
且不依赖复检/改判模块即可完整演示。

**Acceptance Scenarios**:

1. **Given** 系统已维护某产品的国标和客户协议标准，**When** 质量工程师录入该产品的检验值，
   **Then** 系统自动匹配适用标准并输出合格/不合格/需复检/可让步结论，同时展示触发该结论的
   具体标准条款、指标上下限和实测偏差值。
2. **Given** 同一产品同时受国标和客户协议约束，**When** 客户协议要求更严，
   **Then** 判定引擎优先应用客户协议标准，并在判定解释中说明"客户特殊要求"触发原因。
3. **Given** 某检验项目实测值超出合格上限但在让步范围内，**When** 自动判定运行，
   **Then** 结论为"可让步"并显示偏差值和匹配的让步规则。

---

### User Story 2 - 复检与改判流程（Priority: P2）

质量主管需要对"需复检"或存疑结论发起复检，记录复检结果，并在必要时发起改判申请，经审批后
更新最终结论。

**Why this priority**: 复检和改判是钢铁产品质检中的常态业务；在核心判定能力具备后，
复检/改判流程是使系统实际可用的第二优先级。

**Independent Test**: 针对一条"需复检"结论，走完"发起复检 → 录入复检结果 → 发起改判
→ 审批 → 结论更新"全流程，可独立验证。

**Acceptance Scenarios**:

1. **Given** 某批次判定结论为"需复检"，**When** 质量工程师发起复检并录入复检结果，
   **Then** 系统记录复检结果、复检时间、检验人，并重新触发自动判定逻辑。
2. **Given** 复检后结论与原结论不同，**When** 质量主管发起改判申请，
   **Then** 系统记录改判前后结论、改判原因、影响范围，并进入审批流程。
3. **Given** 改判申请已提交，**When** 审批人（质量经理）审批通过，
   **Then** 系统更新最终判定结论，保留完整的改判审批历史记录。

---

### User Story 3 - 让步接收管理（Priority: P3）

销售人员需要对"可让步"结论发起客户让步接收申请，获得客户确认，并记录让步范围、风险说明和
有效期，为后续质保书出具提供依据。

**Why this priority**: 让步接收依赖自动判定给出"可让步"结论，可在 P1 完成后独立实现。

**Independent Test**: 针对一条"可让步"结论，走完"发起让步申请 → 客户确认 → 让步记录"
全流程，可独立验证。

**Acceptance Scenarios**:

1. **Given** 某批次判定结论为"可让步"，**When** 销售人员发起让步接收申请，
   **Then** 系统记录让步范围、风险说明、申请人，并等待内部审批和客户确认。
2. **Given** 让步申请已内部审批通过，**When** 销售人员上传客户确认附件并填写说明文字，
   **Then** 系统记录附件（不可替换）、上传人、时间，confirm_status 变为"已确认"，
   该批次最终标记为"让步接收"。
3. **Given** 让步申请处于"待确认"状态，**When** 超过配置的催促阈值（如发货前 3 天），
   **Then** 系统自动提醒销售人员跟进客户确认，防止发货延误。
4. **Given** 客户明确拒绝让步，**When** 销售人员记录拒绝并可上传拒绝证明，
   **Then** confirm_status 变为"确认驳回"，让步流程终止，产品转入降级或报废处理流程。
5. **Given** 让步有效期到期，**When** 系统检测到过期，
   **Then** 该让步记录自动失效，相关批次状态通知相关责任人。

---

### User Story 4 - 质保书数据汇总与质量统计（Priority: P4）

质量经理需要按卷号或批次汇总关键检验结果用于质保书出具，并通过质量统计视图了解不合格率、
复检率、让步率和指标异常分布。

**Why this priority**: 质保书数据依赖前三个故事的数据沉淀，是系统完整性的收尾功能。

**Independent Test**: 选定一个批次，系统能汇总该批次所有检验指标关键值并展示统计数据，
独立可验证。

**Acceptance Scenarios**:

1. **Given** 某批次已完成所有检验项目，**When** 质量经理按批次查询，
   **Then** 系统汇总该批次所有关键检验指标（成分、性能、尺寸等）及最终判定结论。
2. **Given** 系统已积累一段时间的检验数据，**When** 质量经理查看质量统计报表，
   **Then** 系统展示指定时间段内不合格率、复检率、让步率和各指标异常分布图表。

---

### Edge Cases

- ~~同一产品存在多个版本标准时，判定引擎如何选择适用版本？~~ → 已解决，见 FR-002。
- ~~某检验项目无对应标准条款时，判定结论如何处理？~~ → 已解决，见 FR-005 / FR-006 / FR-015。
- ~~改判申请只能从不合格/需复检发起~~ → 已解决，见 FR-008（任意最终结论均可改判，逆向改判升级审批）。
- ~~改判和让步同时存在同一批次时，最终状态如何合并？~~ → 已解决，见 FR-008 / FR-009。
- ~~检验录入后发现数据录错，如何撤销或更正，且不破坏审计链？~~ → 已解决，见 FR-004b。
- ~~客户协议标准到期后，已有判定结论是否需要重新判定？~~ → 已解决，见 FR-005（判定快照，历史永久有效）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持维护国标、企标、客户协议三类标准，每条标准包含：品种、牌号、
  规格范围、指标上下限、版本号、生效日期（effective_date）、失效日期（expiry_date）、
  状态（草稿/已发布/已作废，仅用于管理，不参与判定）。标准维护 MUST 施加以下约束：
  同一标准体系下（同类型+品种+牌号）的版本有效时间窗口严禁重叠；
  失效日期必须大于生效日期；
  发布新版本时系统 MUST 提示维护人设置旧版本失效日期。
  **不引入 is_current 字段**，有效版本由检验时间与时间窗口交集唯一确定。
- **FR-002**: 判定引擎 MUST 按以下三级优先级匹配标准，产品 MUST 同时满足所命中的所有标准，
  任一不满足则结论为不合格（或按偏差值归入可让步/需复检）：
  - **第一优先级（客户协议标准）**: 匹配条件为客户 + 品种 + 牌号 + 规格 + 检验时间在协议
    有效期内；客户协议可锁定引用旧版国标，系统必须服从合同约定，不得自动替换为新国标。
  - **第二优先级（企标）**: 无客户协议时，按检验时间自动选该品种/牌号下最新有效企标。
  - **第三优先级（国标，底线）**: 无客户协议且无企标时，按检验时间自动选最新有效国标。
- **FR-003**: 系统 MUST 支持维护成分、性能、尺寸、表面、外形五类指标项目及其单位。
- **FR-004**: 检验录入 MUST 包含：炉号、卷号、样品类型、检验项目、检验值、检验时间、检验人；
  支持批量录入。
  **规格选择方式（FR-004 UI 约束）**：检验录入界面中，product_spec 字段 MUST 设计为下拉选择框，
  禁止自由文本输入。下拉数据源为标准库中根据已选客户+品种+牌号动态过滤的有效 spec_range 去重列表。
  显示格式示例："厚度 1.2–2.0mm / 宽度 900–1250mm (GB/T 700-2019)"。系统自动随客户/品种/牌号
  的选择实时缩小规格下拉范围，降低选错概率。一旦选定，该规格与标准版本信息快照存入检验记录，
  后续标准库变更不影响历史判定。
- **FR-004b**: 检验记录提交后数据值永不修改。发现录错时，具有"作废"权限的角色（质检主管或
  原录入人）MUST 执行作废操作，系统强制填写作废原因，自动记录操作人和时间，原记录状态
  变为"作废"并锁定。作废后重新录入正确数据，系统重新触发自动判定。判定引擎和质保书数据
  汇总 MUST 仅取 status = '正常' 的检验记录；所有作废记录完整保留，不可删除。
- **FR-005**: 自动判定 MUST 在检验录入完成后自动触发，输出合格 / 不合格 / 需复检 / 可让步
  四种结论之一，并记录触发依据（标准条款、偏差值、触发规则）。
  **四种结论判断优先级（按序互斥）**：① 所有有标准覆盖的指标均在合格限内 → QUALIFIED；
  ② 任一指标超出合格限，但该指标配置了让步范围（concession_upper/lower 非 NULL）且实测值
  在让步范围内 → CAN_CONCESSION；③ 任一指标超出合格限且**未配置让步范围** →
  NEED_REINSPECTION；④ 任一指标超出合格限且超出让步范围（或在合格限外无让步范围的情况下
  偏差超出可接受阈值）→ UNQUALIFIED。同一批次存在多个失效指标时，结论取最严重级别（优先级
  UNQUALIFIED > NEED_REINSPECTION > CAN_CONCESSION > QUALIFIED）。
  **无标准覆盖指标处理**：若某检验项目在所有命中标准中均无对应指标限值，该项目 MUST
  跳过（不参与整体合格/不合格布尔运算），整体结论由其他有标准覆盖的指标决定；同时将该
  覆盖缺口写入 StandardGap 记录（品种、牌号、指标名称、发现时间、关联检验记录ID），并
  通知标准维护人员补充限值，以驱动标准持续完善。
  **判定快照原则（时间完整性）**：判定引擎在生成 JudgmentEvidence 时 MUST 将所使用标准
  的上下限、版本号、让步范围等关键数值快照至 JudgmentEvidence 记录（冗余存储），而非仅
  保存 standard_id 外键引用。这确保即使原标准到期、被修改或废止，历史判定结论仍可独立
  解释，永不依赖当前标准状态。客户协议到期后，系统 MUST NOT 对已出具结论的历史批次触发
  重新判定；判定以**检验时间**为准，历史结论凝固在检验那一刻的标准快照里。
- **FR-006**: 判定解释 MUST 展示：适用标准名称和版本、各指标偏差值、客户特殊要求说明、
  触发规则描述；对无标准覆盖的指标 MUST 在解释中单独列出并注明"该指标无标准覆盖，未纳
  入本次判定"（不影响最终结论，但对销售/质检/客户完全透明）。
- **FR-007**: 系统 MUST 支持发起复检，记录复检结果、复检原因、责任人，并重新触发判定。
  **复检次数限制**：同一检验记录（含其所有作废/重录版本形成的判定链）最多允许发起 2 次
  复检。第 3 次及以上须走改判流程；系统在发起复检时 MUST 前置校验复检次数，超限时返回
  错误提示"已达最大复检次数，请通过改判流程处理"。
- **FR-008**: 改判申请的状态机与审批规则如下：
  - **任意已出具最终结论**（合格/不合格/可让步/需复检）的批次均可发起改判申请，
    无需先行作废检验记录。
  - **改判类型判定矩阵**（`is_reverse` 字段的权威依据）：
    原结论为 **QUALIFIED（合格）** 或 **CAN_CONCESSION（可让步）** 时，无论目标结论是什么，
    均判定为**逆向改判**（`is_reverse=1`）。
    原结论为 **UNQUALIFIED（不合格）** 或 **NEED_REINSPECTION（需复检）** 时，
    无论目标结论是什么，均判定为**常规改判**（`is_reverse=0`）。
    完整矩阵如下（行=原结论，列=目标结论）：

    | 原结论 \ 目标结论 | QUALIFIED | UNQUALIFIED | NEED_REINSPECTION | CAN_CONCESSION |
    |-----------------|-----------|-------------|-------------------|----------------|
    | QUALIFIED | ❌不可同结论改判 | 逆向 ✦ | 逆向 ✦ | 逆向 ✦ |
    | UNQUALIFIED | 常规 | ❌不可同结论改判 | 常规 | 常规 |
    | NEED_REINSPECTION | 常规 | 常规 | ❌不可同结论改判 | 常规 |
    | CAN_CONCESSION | 逆向 ✦ | 逆向 ✦ | 逆向 ✦ | ❌不可同结论改判 |

    ✦ 逆向改判：MUST 强制填写"新证据来源"和"影响范围"，MUST 上传证据附件；
    审批升级至质量部长或总工（`approval_level=ENHANCED`）；
    系统在操作日志和改判记录中 MUST 添加"逆向改判"特殊标记供审计重点抽查。
    同结论改判（对角线）系统 MUST 在提交前返回 4000 错误，禁止提交。

  - **常规改判**（`is_reverse=0`）：由质检主管审批（`approval_level=NORMAL`）。
  - **逆向改判**（`is_reverse=1`）：由质量部长或总工审批（`approval_level=ENHANCED`）。
  - UI 前置校验：is_reverse=1 时，系统 MUST 弹窗红色警告横幅提示逆向改判，
    强制填写新证据字段后方可提交（提交按钮禁用直至必填字段完整）。
  - 所有改判记录 MUST 保留完整审批历史，数据不可删除。
  - **改判与让步并发处理**：改判审批通过的瞬间，系统 MUST 自动扫描该批次所有关联的进行中
    让步申请（含已审批完成但有效期内的让步），将其 `approval_status` 置为 `INVALID`，
    并写入失效原因"质量结论已变更，让步基础消失"；若让步已完成客户确认，系统 MUST 强制
    触发通知销售人员（"该批次让步已自动撤销，请知会客户"）。
    允许同一批次改判与让步并发进行，无互斥锁定，以改判审批通过时间为分水岭。
- **FR-009**: 让步接收客户确认采用混合策略：
  - **附件（强制）**: 销售人员 MUST 上传客户确认文件（邮件截图、传真件、签字扫描件等），
    系统自动记录上传人和时间；附件上传并确认后不可替换，需更新时 MUST 走"作废原让步申请
    + 重新发起"流程。可选：上传时系统自动添加水印（让步单号 + 上传时间）防止文件复用。
  - **说明文字（可选）**: 销售人员可填写确认摘要（如"客户采购经理张三通过邮件确认，
    主题：关于合同 C2025-088 厚度让步的确认"），不可替代附件。
  - **状态机**: confirm_status MUST 支持：待确认 / 已确认 / 确认驳回。
    客户拒绝时状态为"确认驳回"，可上传拒绝证明，让步流程终止，产品转入降级或报废处理。
    状态长期为"待确认"时（可配置阈值），系统 MUST 自动提醒销售人员跟进。
  - 让步有效期到期后自动失效并通知责任人。
  - 所有状态变更 MUST 记录操作日志（操作人、时间）且不可篡改。
  - 当关联批次的改判审批通过时，让步接收记录 MUST 被系统自动置为 `INVALID` 状态，
    失效原因记录"质量结论已变更，让步基础消失"；系统同步通知销售人员。
- **FR-010**: 质保书数据模块 MUST 支持按卷号或批次汇总关键检验指标，供导出或下游系统使用。
  **"关键检验指标"定义**：默认纳入成分（COMPOSITION）、性能（PERFORMANCE）、尺寸（DIMENSION）
  三类；表面（SURFACE）、外形（SHAPE）默认排除。ADMIN 角色 SHOULD 可通过系统配置调整各类别
  的纳入/排除规则。汇总时仅取 status='NORMAL' 的检验记录，同一指标取最新检验记录的实测值。
- **FR-011**: 质量统计 MUST 支持按时间段查询不合格率、复检率、让步率和各指标异常分布。
- **FR-019（可观测性）**: 系统 MUST 使用 SLF4J + Logback 输出结构化 JSON 应用日志：
  - WARN 级别：可恢复边界情况（标准匹配命中多条取最新版、让步审批超时提醒等）；
    ERROR 级别：需人工干预的故障（判定引擎异常、数据库连接失败、定时任务中断）。
  - 每条日志 MUST 包含 timestamp、level、logger、thread、message 和 context（至少含业务主键及 traceId）；禁止非结构化字符串拼接。
  - 每个 HTTP 请求 MUST 通过 MDC 自动生成并传播 traceId，使同一请求所有日志可串联。
  - logback-spring.xml 配置 File Appender，WARN 及以上级别写入 `/var/log/qc/application-error.log`，按日滚动，保留 30 天。
  - 定时任务（ConcessionScheduler 等）MUST 在任务开始/结束时输出 INFO 日志（含任务名和执行时长），异常时输出 ERROR 日志。
  - Spring Boot Actuator `/actuator/health` 端点 MUST 暴露，供反向代理健康检查。
- **FR-012**: 权限审计 MUST 区分以下角色权限：标准维护（质量工程师）、检验记录作废（质检主管
  或原录入人）、改判审批（质量经理）、让步审批（质量经理 + 销售经理）；所有关键操作 MUST
  记录审计日志（操作人、时间、变更内容），日志不可删除或修改。
- **FR-013**: 质量工作台 MUST 以看板形式展示：待判样品数、不合格批次、待处理复检任务、
  待审批让步申请。
- **FR-014**: 系统 MUST 提供独立账号管理：用户名 + 密码登录，后端通过 JWT Token 进行无状态
  鉴权；网关层统一校验 Token 有效性；Token 过期后用户需重新登录；密码 MUST 加密存储（不可
  逆哈希）。系统不对接外部 SSO/LDAP/OAuth2（预留扩展接口但初期不实现）。
- **FR-015**: 系统 MUST 维护 StandardGap（标准覆盖缺口）记录：当判定引擎遇到无标准覆盖的
  检验指标时，自动写入缺口记录（品种、牌号、指标名称、首次发现时间、关联检验记录ID）；
  系统 MUST 通知标准维护人员（工作台提示或消息），驱动标准补充；缺口记录供质量工程师在
  标准库管理页查看和处理。
- **FR-016**: 所有系统通知 MUST 通过**站内消息中心**投递（不依赖外部邮件/IM 服务）。
  通知场景包括：让步超时未确认提醒（销售人员）、让步因改判自动失效通知（销售人员）、
  StandardGap 覆盖缺口通知（质量工程师）、让步有效期到期通知（责任人）。
  工作台 MUST 展示未读通知数量角标；用户点击可跳转到相关业务记录。
  初期不对接外部邮件/企微/钉钉（接口预留，可后续扩展）。
- **FR-017（数据字典）**: 系统 MUST 维护统一的数据字典（SysDict + SysDictItem）。
  所有前端下拉框数据 MUST 从数据字典动态获取，禁止前端硬编码枚举值。
  纳入字典管理的枚举项包括但不限于：标准类型（STANDARD_TYPE）、指标类别
  （INDICATOR_CATEGORY）、样品类型（SAMPLE_TYPE）、判定结论类型（JUDGMENT_TYPE）、
  标准状态（STANDARD_STATUS）、检验记录状态（INSPECTION_STATUS）、改判审批级别
  （APPROVAL_LEVEL）、让步确认状态（CONFIRM_STATUS）、操作审计类型
  （AUDIT_OPERATION_TYPE）、用户角色（USER_ROLE）等。
  后端 MUST 提供字典查询接口，前端启动时统一加载并缓存于 Pinia dictStore；
  字典维护界面仅 ADMIN 角色可操作。
- **FR-018（表头筛选）**: 系统所有数据列表页的表格 MUST 提供表头列筛选功能。
  每列筛选条件 MUST 通过后端接口动态查询（非前端本地过滤），支持文本模糊搜索、
  枚举值多选（下拉字典项）、日期范围选择三种筛选类型；
  筛选条件变更时自动触发分页查询（回到第一页）；
  筛选状态在页面刷新后 SHOULD 保留（URL query 参数持久化）。

### Key Entities

- **QualityStandard（质量标准）**: 标准类型（国标/企标/客协）、品种、牌号、规格范围、版本号、
  effective_date（生效日期）、expiry_date（失效日期，可为 9999-12-31 表示尚未失效）、
  status（草稿/已发布/已作废，仅管理用）、关联客户（客协专属）；
  包含多条 **StandardIndicator（标准指标）**（指标项目、上限、下限）。
  **约束**：同标准体系下版本时间窗口唯一不重叠；无 is_current 冗余字段。
- **InspectionRecord（检验记录）**: 炉号（heat_no）、卷号（coil_no）、批次号（batch_no）、
  样品类型、检验时间、检验人、status（正常/作废）、void_reason（作废原因，作废时必填）、
  void_by（作废操作人）、void_time（作废时间）；包含多条 **InspectionValue（检验值）**
  （指标项目、实测值）。数据值字段提交后永不修改；无版本历史表，无 is_current 字段。
  **批次号规则**：同一炉号（heat_no）下的多个钢卷共享同一批次号（多对一关系）；批次号
  由炉号衍生生成（如 `batch_no = heat_no` 或业务前缀+炉号）；质保书数据汇总（FR-010）
  和质量统计（FR-011）均以批次号为聚合键，一次汇总覆盖同批次所有卷的检验记录。
- **JudgmentResult（判定结论）**: 关联检验记录、适用标准、结论类型、判定时间；包含多条
  **JudgmentEvidence（判定依据）**（触发标准条款、偏差值、触发规则）。
- **ReinspectionRecord（复检记录）**: 关联原判定结论、复检原因、复检结果、责任人、状态。
- **ReJudgmentRequest（改判申请）**: 改判前结论、改判后结论、改判原因、影响范围、
  is_reverse（是否逆向改判，布尔）、new_evidence_source（新证据来源，逆向改判时必填）、
  evidence_attachment（证据附件，逆向改判时必填）、审批级别（常规/增强）、审批状态、
  审批记录列表（含审批人、时间、意见）。
- **ConcessionAcceptance（让步接收）**: 关联判定结论、让步范围、风险说明、有效期、
  confirm_status（待确认/已确认/确认驳回）、confirm_attachment（确认文件附件，强制，
  上传后不可替换）、confirm_note（确认说明文字，可选）、附件上传人、上传时间；
  让步状态（审批中/已批准/已失效/已驳回）。
- **QualityCertData（质保书数据）**: 关联批次号、汇总检验指标快照、生成时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 质量工程师完成一次完整检验录入到获得带依据的判定结论，全程不超过 3 分钟。
- **SC-002**: 自动判定结论与人工抽查结论的一致率不低于 99%（基于已维护标准范围内的样本）。
- **SC-003**: 复检 → 改判 → 审批全流程操作步骤不超过 10 步。
- **SC-004**: 质量工作台首页加载时间不超过 3 秒（含待判/不合格/复检/让步实时汇总数据）。
- **SC-005**: 质保书数据汇总操作：从选定批次到生成汇总数据不超过 10 秒。
- **SC-006**: 权限审计日志 100% 覆盖标准维护、改判审批、让步审批三类关键操作，日志不可篡改。
- **SC-007**: 系统上线后，销售和生产人员对判定依据的"无法复核"投诉降低 80% 以上。
- **SC-008**: 系统可用性目标（软可用）：单点部署，MySQL 或 Redis 故障时系统进入不可用状态并向用户展示维护提示页；故障恢复后系统 MUST 自动恢复正常服务，无需人工干预；RTO（恢复时间目标）≤ 30 分钟；RPO（数据恢复点目标）= 0（所有业务操作均在 MySQL 事务内完成，无数据丢失）。

## Assumptions

- 系统采用前后端分离架构，前端 Vue 3 + Element Plus，后端 **Spring Boot 2.7.x 单体** + MySQL + Redis；
  认证采用 Sa-Token（轻量级权限认证框架），不使用 Spring Cloud 微服务架构；
  不对接外部 SSO/LDAP/OAuth2。
- 数据库版本：**MySQL 5.7.43**（不支持 CTE、窗口函数；统一 utf8mb4_unicode_ci 字符集）。
- 缓存版本：**Redis 8.0.5**（JWT 黑名单、Dashboard 缓存 TTL 60s、字典缓存 TTL 10min）。
- 初期用户规模约 50–200 人，并发判定请求峰值不超过 100 次/分钟。
- 客户协议标准由系统内部维护，不对接外部标准数据库（外部标准导入为未来扩展）。
- 审批流程为固定两级审批，不支持自定义审批链（自定义工作流为未来扩展）。
- 质保书出具本系统只负责数据汇总，最终 PDF 生成由下游系统或人工处理。
- 移动端支持为浏览器自适应，不开发原生 App。
- 数据保留策略遵循行业默认：检验记录和审计日志保留 10 年。

## Clarifications

### Session 2026-05-14

- Q: 同一产品存在多个版本标准时，判定引擎如何选择适用版本？ → A: 三级优先级匹配（客户协议 > 企标 > 国标）；同级内按检验时间自动取有效时间窗口内的版本（无重叠约束保证唯一性）；客户协议可锁定引用旧版国标，系统不自动替换；产品需同时满足所有命中标准；QualityStandard 使用 effective_date + expiry_date 时间窗口，不引入 is_current 字段，status 仅用于管理流程。
- Q: 检验录入后发现数据录错，如何更正且不破坏审计链？ → A: Option B（软作废 + 重新录入）：错误记录由有权限角色执行作废（强制填写原因，自动记录操作人/时间），原记录状态变为"作废"并锁定数据值永不修改；重新录入正确数据触发重新判定。判定引擎仅取 status='正常' 记录。无版本历史表，InspectionRecord 追加 status/void_reason/void_by/void_time 四字段即可满足审计要求。
- Q: 用户如何登录系统？ → A: Option B — 系统独立账号，用户名+密码登录，JWT Token 鉴权，网关统一校验；密码不可逆哈希存储；不对接 SSO/LDAP/OAuth2（预留接口）。
- Q: 让步接收中"客户确认"如何记录？ → A: 混合策略（B+A）：强制上传客户确认附件（邮件截图/传真件/签字扫描件，上传后不可替换，可加水印），可选填写确认摘要文字；confirm_status 支持待确认/已确认/确认驳回三态；客户拒绝时流程终止转降级/报废；长期待确认时自动提醒销售；附件上传后不可替换，需更新须走作废重申流程；所有状态变更记入不可篡改审计日志。
- Q: 改判申请允许从哪些原始结论状态发起？ → A: 升级版 Option C：任意已出具最终结论均可发起改判（含合格批次）；分常规改判（质检主管审批）和逆向改判（合格/可让步→更差结论，质量部长/总工审批，强制填写新证据来源+上传证据附件+影响范围，系统标记"逆向改判"供审计抽查）；UI 对逆向改判弹窗警示并强制字段前置校验。

### Session 2026-05-15

- Q: 某检验项目无对应标准条款时，判定结论如何处理？ → A: Option C + D 混合：该指标跳过（不参与整体合格/不合格布尔运算），整体结论由有标准覆盖的其他指标决定；判定解释中单独列出"无标准覆盖"说明（对销售/质检/客户完全透明）；同时旁路写入 StandardGap 记录（品种/牌号/指标名称/关联检验记录ID）并通知标准维护人员补充，驱动标准持续完善。
- Q: 改判与让步同时存在同一批次时如何处理？ → A: Option B（允许并发，改判优先）：改判审批通过瞬间，系统自动将该批次所有进行中及已完成的让步申请置为 INVALID，失效原因"质量结论已变更，让步基础消失"；若让步已客户确认，强制通知销售人员知会客户；无互斥锁定，以改判审批通过时间为分水岭。
- Q: 客户协议标准到期后，已有判定结论是否需要重新判定？ → A: Option A（永不重判）+ 判定快照设计：判定以检验时间为准，历史结论凝固在检验那一刻的标准快照里，永不受标准到期/修改影响。JudgmentEvidence 快照存储标准上下限等关键数值（冗余，非仅外键），历史结论可独立解释，无需查询当前标准状态。
- Q: 批次号与卷号的业务关系是什么？ → A: Option B（多对一）：同一炉号下的多个钢卷共享一个批次号；批次号由炉号衍生；质保书汇总和统计均以批次号为聚合键，一次覆盖同批次所有卷。
- Q: 系统通知的投递方式？ → A: Option A（站内消息）：所有通知通过系统内消息中心投递，工作台展示未读角标，点击跳转业务记录；不依赖外部邮件/IM，接口预留供后续扩展。
- Q: 同一批次最多允许发起几次复检？ → A: Option B（最多 2 次）：超限须走改判流程；系统前置校验，超限返回错误提示。

### Session 2026-05-16

- Q: "需复检"（NEED_REINSPECTION）结论的触发条件是什么？ → A: Option A：实测值超出合格限且**该指标未配置让步范围**（concession_upper/lower 均为 NULL）时，结论为 NEED_REINSPECTION；若该指标配置了让步范围且实测值落在让步范围内，则结论为 CAN_CONCESSION；若实测值超出让步范围，则结论为 UNQUALIFIED。三者互斥，判断顺序为：① 在合格限内→QUALIFIED；② 在让步范围内（且已配置）→CAN_CONCESSION；③ 超出合格限且无让步范围→NEED_REINSPECTION；④ 超出让步范围（或合格限外且无让步范围）→UNQUALIFIED。
- Q: 检验录入中 product_spec 规格字段如何与标准库 spec_range 匹配？ → A: Option A + UI 约束补充：product_spec 禁止自由文本输入，MUST 设计为下拉选择框；数据源为标准库中按已选客户+品种+牌号动态过滤的有效 spec_range 去重列表；显示格式如"厚度 1.2–2.0mm / 宽度 900–1250mm (GB/T 700-2019)"；选定后快照存入检验记录，历史判定不受后续标准变更影响。系统不做区间数值解析，由下拉设计兜底人工选择的准确性。
- Q: 质保书"关键检验指标"的范围如何定义？ → A: Option C：成分（COMPOSITION）、性能（PERFORMANCE）、尺寸（DIMENSION）三类固定纳入；表面（SURFACE）、外形（SHAPE）默认排除；ADMIN 可通过系统配置调整各类别的纳入/排除规则。
- Q: 系统可用性 / 故障恢复目标是什么？ → A: Option B（软可用）：单点部署，MySQL/Redis 故障时系统不可用并展示维护提示；恢复后自动恢复服务，无需人工干预；RTO ≤ 30 分钟，RPO = 0（事务保证无数据丢失）。已新增为 SC-008。
- Q: 系统可观测性（日志/监控）要求是什么？ → A: Option B + 详细规范：SLF4J + Logback 结构化 JSON 日志；WARN（可恢复边界）/ ERROR（需人工干预）分级；MDC 自动注入 traceId 串联同一请求所有日志；File Appender 写入 /var/log/qc/application-error.log（按日滚动 30 天）；定时任务开始/结束输出 INFO + 异常 ERROR；Actuator /health 端点暴露。已新增为 FR-019。
